# V5.1：随地图增长的耗时优化

2026-10-20。正式界面和Beta共用，启动方式不变。根据本机test_111/setp1实拍日志，前后段视觉跟踪总耗时中位约89/78ms，稠密地图更新却从0.84秒增长到40.86秒，主要瓶颈是历史地图重融合，绘图本身仍约3–5ms。

## 修改

- 撤销节点只访问parts中该节点引用的体素，移除原先对整张cells表的删除扫描；通过数据库集合操作更新、回填体素贡献。事务及每格一个质心规则保持。
- 原生优化后只标记变化节点。实时重融合按最大点位移上界判断：平移差范数＋该节点最大半径×旋转矩阵差的谱范数。小于0.75mm（3mm体素的四分之一）的修正暂缓；每次均与最后已融合位姿比较，累计变化不会丢失。
- 较大修正每次发布最多处理一个历史节点，优先新增观测，历史节点按上次融合次序公平推进。没有新观测时，稠密线程也继续排空变化节点。单个大节点依然可能耗时，预算不是毫秒级硬实时保证。
- 未改变的地图复用只读快照，界面更新轨迹时不重复复制和上传完整点云；未增加点数上限。
- 点击完成后停止前端，排空已接收任务，再对所有保留节点按最终位姿完整融合。实时预览可短暂包含尚未校正的历史节点，最终主地图不沿用实时近似或分批预算。大回环后的完成操作仍可能需要数十秒。
- 保存直接使用完整融合主地图，不再自动调用rtabmap-export重新生成未参与后续处理的RGB对齐副地图。test_111中该副本达3,456,083,856字节。map.db保留原生图，独立RGB-D/标定/局部观测保留，map_poses.txt由保留节点位姿导出（仅稠密节点），二至五阶段仍从原有数据接口读取。

## 日志与边界

fusion_details.jsonl新增：updated_nodes、deferred_small_pose_nodes、pending_pose_nodes、fusion_ms、cloud_read_ms及force。原preview_metrics.csv继续记录总融合耗时；online_metrics.csv用于判断定位是否变慢。

这次没有设置原生WM数量/时间阈值，也没有实现子地图/空间块显示。全图读取和GPU上传仍随总点数增长；较大的回环重融合只是分批执行，保存时工作量仍随待修正节点增长。不能将本次改动解释为恒定总内存或无限地图下的固定耗时。

测试使用已有扫描副本，无实机拍摄。实测、缓存抖动对照、较大修正预算及最终一致性记录见results/map_scaling_v5_1/REPORT.md。旧扫描和旧包继续保留；新包以20261020_v5_1命名。
